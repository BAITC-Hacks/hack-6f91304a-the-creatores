# Расчётный модуль участника №2

Модуль читает бизнес-данные XLSX через уже установленный `openpyxl`, проверяет
их, прогнозирует спрос и рассчитывает закупку. Новые зависимости не требуются.
Реальных Excel-файлов и примеров компании в исходном репозитории не было:
алиасы ниже — поддерживаемый интерфейс, а не результат анализа данных компании.
Тесты создают исключительно синтетические книги во временных каталогах.

## Подключение к существующему backend

`backend/config.py` уже использует `backend.calculations.provider` по умолчанию.
При `DEMO_MODE=false` работают две функции существующего контракта:

```python
from pathlib import Path
from backend.calculations.provider import prepare_dataset, calculate, calculate_detailed
from backend.models import CalculationParameters

prepared = prepare_dataset([Path("your-data.xlsx")])
if not prepared.report.valid:
    raise ValueError(prepared.report.errors)

parameters = CalculationParameters(
    calculation_date="2026-09-01",
    lead_time_days=10,
    review_period_days=20,
    safety_stock_days=5,
)
result = calculate(prepared.payload, parameters)  # ProviderResult
detailed = calculate_detailed(prepared.payload, parameters)  # JSON-compatible dict
evidence = detailed["recommendations"][0]["explanation"]
```

`prepare_dataset(files, sources=None)` принимает пути и необязательные `Source`
в том же порядке. Исходное имя файла берётся из `Source.filename`, поскольку
backend сохраняет книги под UUID. Ошибки Excel возвращаются отчётом, а не
подменяются демонстрационными данными. `calculate` принимает нормализованный
payload версии 1 и `CalculationParameters` либо словарь тех же параметров.
Неверные данные или неподдерживаемая версия вызывают `ValueError` при прямом
вызове; HTTP backend предварительно блокирует ошибочный набор ответом 422.
Функции не изменяют переданные данные, не обращаются к сети и не создают ID.

## Формат Excel

Поддерживаются несколько файлов и листов; строка заголовков должна находиться
среди первых 20 строк. Каждый непустой лист должен иметь колонку SKU. Пустой
лист вызывает предупреждение. Объединение выполняется по SKU. Конфликт имени,
поставщика, единицы или закупочного условия для одного SKU — ошибка, а не выбор
случайного значения. Разные поставщики одного SKU требуют согласования отдельной
модели ключа; текущая загрузка их не объединяет молча.

| Поле | Примеры поддерживаемых заголовков |
| --- | --- |
| SKU | `sku`, `Артикул`, `Код товара` |
| Название | `name`, `Наименование`, `Товар` |
| Поставщик | `supplier`, `vendor`, `Поставщик` |
| Единица | `unit`, `uom`, `Ед. изм.` |
| Текущий остаток | `stock`, `on hand`, `Остаток`, `Остаток на складе` |
| Минимальная партия | `moq`, `Минимальный заказ`, `Минимальная партия` |
| Кратность | `order_multiple`, `pack size`, `Кратность`, `Упаковка` |
| Срок в днях | `lead_time_days`, `lead time`, `Срок поставки` |
| Месяц продаж | `month`, `period`, `Месяц`, `Период` |
| Продажи | `sales_quantity`, `sales`, `Продажи` |
| Дни без товара | `stockout_days`, `Дни отсутствия`, `Дни без товара` |
| Количество в пути | `incoming_quantity`, `incoming`, `В пути` |
| Прибытие | `incoming_date`, `arrival_date`, `eta`, `Дата поставки` |
| Коэффициент сезонности | `seasonality`, `Коэффициент сезонности` |

Регистр, пробелы, подчёркивания и пунктуация заголовков нормализуются.
Полный список — `excel_loader.DEFAULT_ALIASES`. Для нестандартной выгрузки можно
дополнить его без изменения исходных файлов:

```python
from backend.calculations.excel_loader import load_workbooks

loaded = load_workbooks(paths, sources, aliases={"stock": ["Доступно, шт"]})
```

Продажи задаются либо длинной таблицей `sku, month, sales_quantity`, либо широкой
таблицей `sku, 2026-01, 2026-02, ...`. Заголовками могут быть даты Excel и месяцы
в виде `01.2026`, `Январь 2026`. Даты месячных итогов приводятся к первому числу;
это **месячные итоги**, не журнал отдельных продаж. Две записи одного SKU за один
месяц считаются неоднозначным дублем, автоматически не суммируются.
Для широкой истории дни отсутствия можно дать в колонках `stockout_days 2026-01`.

Поставки задаются строками `sku, incoming_quantity, incoming_date`; несколько
поставок одного товара допустимы. Период прибытия должен быть известен.
Явный `incoming_quantity=0` допустим без даты. Отсутствие строки товара в листе
поставок не доказывает отсутствие поставок: итог остаётся неизвестным.

Сезонность: строки `sku, month, seasonality`, где месяц — число 1–12 или его имя;
либо лист с названием, содержащим «сезон»/`season`, с колонками месяцев 1–12.
Коэффициенты положительны. Для неуказанных месяцев используется нейтральная
поправка 1 с предупреждением. Это допущение алгоритма, не добавленная запись Excel.

Общие заголовки `quantity`/«Количество» и `date`/«Дата» распознаются по названию
листа/исходного файла: «остатки»/`stock`, «в пути»/`incoming`, иначе как продажи.
Для неоднозначных книг используйте явные заголовки из таблицы.

Текстовые SKU сохраняют ведущие нули; целочисленные SKU преобразуются в строки.
Для числового SKU поддерживается маска Excel вида `000000`. Если Excel уже потерял
нули или точность длинного числового артикула, восстановить их нельзя; храните
такие артикулы текстом. Числа поддерживают пробелы-разделители и десятичную запятую;
неоднозначные сочетания запятой и точки отклоняются. Формулы не вычисляются:
используется сохранённый результат Excel, а отсутствие кэша вызывает предупреждение.

## Проверка данных

`validation.validate_dataset(payload)` возвращает `valid`, `business_validation`,
списки `errors` и `warnings`. Машиночитаемые детали находятся в `summary.issues`:

```json
{"code": "missing_optional_field", "severity": "warning",
 "message": "SKU 000123: Неизвестно поле stock.",
 "source": null, "sheet": null, "row": null,
 "sku": "000123", "field": "stock"}
```

Ошибки блокируют расчёт: отсутствующий SKU, имя или поставщик (последние два
обязательны по текущему API), конфликтующие значения, дубли, нечисловые/отрицательные
количества, неверные даты, MOQ < 0, кратность ≤ 0, некорректный срок поставки.
MOQ=0 означает отсутствие минимального ограничения, а не кратность.

Предупреждения отмечают неизвестные остатки, историю, поставки, срок, единицу,
MOQ и кратность. Неизвестные количества остаются `null`. При отсутствии спроса,
остатка или информации о поступлениях заказ также `null`, срочность `unknown`.
Отсутствие MOQ/кратности разрешает расчёт без этих ограничений с предупреждением.
Все количества одного SKU должны быть в одной единице; конвертация единиц не выполняется.

## Прогноз и заказ

1. Из истории берутся только завершённые месяцы до месяца даты расчёта; текущий
   неполный месяц и будущие записи исключаются. По умолчанию окно — последние
   6 календарных месяцев, вес месяца возрастает от 1 до 6. Пропуски не равны нулю.
2. Продажи делятся на календарные дни. Если число дней отсутствия известно,
   знаменатель — дни наличия. Это оценка скорости продаж при допущении её
   равномерности, не утверждение о количестве потерянных продаж. Полностью
   недоступный месяц исключается. Без истории наличия нулевые продажи остаются
   наблюдаемым нулём с предупреждением о возможной недооценке.
3. Если сезонность задана, история очищается от неё, а будущая сезонность применяется
   пропорционально дням месяцев прогнозного периода. Автоматическая оценка возможна
   при 24 последовательных пригодных месяцах: убирается устойчивый логарифмический
   тренд, сравниваются годовые повторы. Противоречивые повторы дают нейтральную
   сезонность с предупреждением. Слишком короткая история её не доказывает.
4. Высокие всплески ограничиваются порогом `median + max(3 × MAD, 2 × median)`.
   Для двух наблюдений опорой служит меньшее; одно наблюдение не позволяет надёжно
   выявить выброс. Исходные и скорректированные значения сохраняются в объяснении.
5. Тренд оценивается устойчивым наклоном Theil–Sen при ≥4 последовательных месяцах
   без скорректированных выбросов и поддержке направления минимум 2/3 шагов.
   Изменение менее 3% в месяц не считается устойчивым трендом. Проекция к середине
   прогнозного периода ограничена ±25%. Явный `demand_growth_adjustment` заменяет
   автоматическую поправку тренда, чтобы не считать рост дважды.
6. Горизонт: `[calculation_date, calculation_date + lead_time_days + review_period_days)`.
   Страховой запас = средний прогнозный дневной спрос × `safety_stock_days`.
   Он не удлиняет горизонт спроса. Поставки включаются только при попадании даты
   в этот полуоткрытый интервал. Просроченные исключаются с предупреждением.
7. `need = forecast_demand + safety_stock - stock - incoming_in_period`.
   Если `need ≤ 0`, заказ равен 0. Иначе применяется минимум MOQ, затем округление
   вверх до известной кратности. MOQ сам по себе не является кратностью.
   При отсутствии кратности дробное количество сохраняется. У границы упаковки
   устраняется погрешность вычислений в пределах `1e-12` упаковки; положительный
   заказ не обнуляется и явный MOQ не уменьшается.

Существующий API передаёт один обязательный `lead_time_days` на весь сценарий.
Он явно переопределяет сроки из Excel; расхождение или отсутствие исходного срока
отмечается предупреждением. Исходный и применённый сроки сохранены отдельно.
Автоматическое применение разных сроков к SKU потребует согласовать контракт
с участником №3: сервер сейчас проверяет общий горизонт.

`urgency=high` означает возможный временный дефицит в течение горизонта по среднему
дневному прогнозу с учётом дат имеющихся поступлений и предполагаемого прибытия
рекомендованного заказа через заданный срок; `medium` — положительный заказ без
такого дефицита; `none` — заказ не требуется; `unknown` — данных недостаточно.
Даже нулевой заказ может иметь высокую срочность, если достаточная суммарная поставка
приходит слишком поздно. Срочность — оценка, а не точное дневное моделирование сезонности.

Параметры прогноза вынесены в аргументы `forecast_demand` и константы `demand.py`.
Для прямого подробного расчёта их можно передать через `forecast_options`.
Отсутствие свежих данных не заменяется искусственными продажами; если в окне нет
пригодной истории, прогноз неизвестен. Никаких случайных чисел и зависимости от
текущей даты системы нет: одинаковые входы дают одинаковые результаты.

## Что передать участнику №3

Существующий `calculate()` совместим с `ProviderResult` без изменения чужих файлов.
`reason` содержит фактическую арифметику, базовый спрос и сезонность; предупреждения
доступны в строке рекомендации. Текущий API допускает максимум 100 предупреждений
на строку; при превышении последний элемент сообщает число пропущенных записей.
Полный список и объяснение возвращает `calculate_detailed()`:
использованные месяцы/веса, спрос, сезонные коэффициенты, классификацию и поправку
тренда, аномалии, остаток, включённые поставки, страховой запас, сроки, MOQ,
кратность, исходную потребность и итог заказа.

Для сохранения полного объяснения и передачи его ИИ участнику №3 потребуются
следующие изменения **в его зоне ответственности** (здесь они не внесены):

- `backend/models.py`: согласовать типизированное поле объяснения или отдельную
  структуру результата; текущие модели запрещают дополнительные поля.
- `backend/services/calculations.py`: принимать и сохранять подробный результат
  либо вызывать `calculate_detailed()` и сохранять объяснения рядом с расчётом.
- `backend/agent/tools.py`: возвращать сохранённое объяснение выбранного SKU
  в `explain_sku`; ИИ не должен заново вычислять количества.
- При расширении публичной модели обновить `contracts/openapi.json` и пример
  через существующий генератор и проверить экспорт/API. Полный payload Excel
  для объяснения передавать модели не нужно.

Объяснение надо сохранять вместе с результатом и применёнными параметрами: поздний
пересчёт после изменения алгоритма не гарантирует того же исторического решения.

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m ruff check backend contracts tests
.venv/bin/python -m ruff format --check backend contracts tests
```

В Windows используйте `.venv\Scripts\python.exe` вместо `.venv/bin/python`.
Покрыты арифметика, MOQ/кратность, границы дат, неизвестные значения, сезонность,
тренд, выбросы, отсутствие товара, детерминизм, чтение/слияние XLSX, ошибки и
реальная интеграция загрузки/расчёта/сохранения с существующим FastAPI.
